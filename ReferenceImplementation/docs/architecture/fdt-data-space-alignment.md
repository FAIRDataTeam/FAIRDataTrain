## 0. Glossary

| Term | Meaning (as used here) |
|---|---|
| **IDSA / IDS-RAM / Rulebook** | International Data Spaces Association; its Reference Architecture Model (4.2 archived; new generation in draft) and its normative **Rulebook** (2026-2) of must/should/may requirements for data spaces |
| **DSP — Dataspace Protocol** (Eclipse Dataspace WG, 2025-1) | Protocol suite for data spaces: Catalog Protocol (DCAT + ODRL offers), Contract Negotiation Protocol (offer → agreement state machine), Transfer Process Protocol; JSON-LD messages; submitted to ISO/IEC JTC 1 as a PAS |
| **DCP — Decentralized Claims Protocol** (Eclipse, 1.0.1) | Identity-and-trust overlay for DSP: participants identified by **DIDs**, self-issued JWT tokens, a Credential Service per participant from which verifiers fetch **Verifiable Presentations**, a Credential Issuance Protocol and profiles fixing data model, revocation and signatures; submitted to ISO/IEC with DSP |
| **DID — Decentralized Identifier** (W3C) | A resolvable identifier (e.g. `did:web:station.utwente.nl`) whose DID document publishes the holder's public keys and service endpoints |
| **VC / VP — Verifiable Credential / Presentation** (W3C VC Data Model 1.1 / 2.0) | A digitally signed, machine-verifiable statement by an *issuer* about a *subject* (legal entity, certification, affiliation, authorisation), held by the subject and presented to a *verifier* as a Verifiable Presentation; revocation via status lists |
| **EDC — Eclipse Dataspace Components** | Reference open-source implementation of DSP/DCP connectors, used by Simpl and many data spaces |
| **Simpl / Simpl-Open / Simpl-Live** | The European Commission's open-source data-space middleware (DSP-based, EDC-integrated) and its deployments for EU initiatives (EHDS secondary use, EOSC, …) |
| **Gaia-X / GXDCH / DUA** | Gaia-X European Association's trust framework; Gaia-X Digital Clearing House (compliance, registry, notary services); Data Usage Agreement — the rights holder's authorisation attached to a data product contract |
| **DSSC Blueprint** | Data Spaces Support Centre's reference model of building blocks and service layers for European data spaces (v3.0, final) |
| **ODRL / DCAT / PROV-O / SHACL** | W3C vocabularies for policies, catalogues, provenance and shape validation used throughout |
| **EHDS / HDAB / SPE** | European Health Data Space Regulation (EU) 2025/327; Health Data Access Body (issues data permits); Secure Processing Environment (Art. 73) |
| **DGA / Data Act** | Data Governance Act (Reg. 2022/868): data intermediation services, data altruism, SPE definition; Data Act (Reg. 2023/2854): essential requirements for data-space participants (Art. 33), smart contracts (Art. 36) |
| **PEP / PDP / PAP / PIP / PXP** | Policy enforcement, decision, administration, information and execution points (XACML/IDS usage-control vocabulary) |
| **eIDAS 2 / EUDI Wallet** | Regulation (EU) 2024/1183 and the EU Digital Identity Wallet for person-level credentials *(not verified in this session)* |

**Corrections to the v0.2 candidate mapping.** (a) "IDS-RAM" should be read as Rulebook 2026-2 + DSP/DCP for anything normative; IDS-RAM 4.2 remains useful for the connector anatomy and usage-control vocabulary (PEP/PDP/PIP/PXP/PMP). (b) The Rulebook explicitly recognises the FDT paradigm: "When data is not moved but a 'code to data' approach is selected, the push and pull behaviour is reversed: The consumer participant provides a data asset containing code (source code, compiled library, signed container) to the participant providing the data." (§110) and names "confined compute" as the strong-enforcement option for high-sensitivity data (§105). (c) Gaia-X has no compute-to-data concept of its own; it appears in the Gaia-X ecosystem via Pontus-X / Ocean Protocol. (d) The DSSC Blueprint v2.0 building-block names used in v0.2 are superseded by v3.0's service-layer view.

### A. Identity and trust

| Req. | Requirement | FDT element | Now | Proposal | Horizon |
|---|---|---|---|---|---|
| A1 | Every participant is a legal organisation operating software agents; trust is established by "procedures, evidence categories, and decision rules" agreed in the data space (Rulebook §102 "Establishing trust"; IDS-RAM 4.2 §3.2 "Each participant … must undergo certification") | Station owner, **Data Controllers** (they author the offers and approve agreements — in IDS-RAM 4.2 terms the *Data Owner*, in Gaia-X the *Data Rights Holder / Licensor* who issues the Data Usage Agreement), Handler operator, Garage/Directory operators, Individual Gateway operator | ✗ | Define an FDT participation profile (evidence categories, onboarding) for **each participant class, including data controllers**: a controller's authority over a resource must itself be evidenced (who may bind the controller organisation; delegation to a data steward), because the effective decision is controller offer ∧ owner policy (ADR-011). Keep it light for research use but explicit | v1 |
| A2 | Participant identity: "DIDs and verifiable credentials are the recommended approach, while functionally equivalent implementations may be acceptable if they preserve participant autonomy and interoperability" (Rulebook §102); "Attributes and self-description should always be available as verified presentations" (§107) | Identity (ADR-010) | ◐ | Keep federated OIDC for v1 as the "functionally equivalent" option; make station and train self-descriptions signable now (VC-ready) | v1 → v2 |
| A3 | DCP conformance (for ISO-aligned trust): participant ID "MUST be a DID"; Self-Issued ID Token (iss = sub = own DID, aud = verifier DID, jti, exp, iat) in `Authorization: Bearer`; a `CredentialService` in the DID document; verifiers validate signature, revocation, expiry; credentials in one presentation homogeneous; profiles `vc20-bssl/jwt` or `vc11-sl2021/jwt` | Station PEP 1, Handler, Garage | ✗ | Plan the VC phase as DCP adoption (not a home-grown VC scheme); pick a profile; decide who runs the trusted-issuer list (A4) | v2 |
| A4 | A Data Space Governance Authority maintains trusted issuers / participant registration (DCP trust model; Rulebook DSGA) | FDT governance | ✗ | Name the FDT governance function (who issues "station", "approved researcher", "vetted train" credentials) — an organisational decision with technical consequences | v1 (decision), v2 (tech) |
| A5 | Transport security bound to identity: encrypted, integrity-protected connections; peer certificate fingerprint bound to the token (IDS-RAM 4.2 §3.2, §4.1.2) | Dispatch gateway, station-to-station forwarding | ◐ | mTLS between Handler and stations; mandatory for P10 station-to-station forwarding | v1 |
| A6 | Gaia-X compliance (optional label track): Participant credential = Legal Person + Legal Registration Number (GXDCH notary) + Terms-and-Conditions VCs; did:web with proof of control; VC Data Model 2.0, VC-JWT, issuer keys chaining (`x5c`/`x5u`) to approved trust service providers; validated by a GXDCH Compliance Service | Every FDT organisation | ✗ | Not for v1; note that Gaia-X requires did:web + VC, so the DCP path (A3) also serves Gaia-X | later |
| A7 | **Data controllers as identified parties.** The agreement's `assigner` must be a dataspace identifier of the party that grants the rights (DSP: "An Agreement MUST contain an `assigner` and `assignee`"); Gaia-X requires the Data Product Provider to "have the legal authorization from the `Data Producer`(s)" and every contract to embed DUAs "provided by the `Data Licensor(s)`" (Compliance D1.1.3, D1.1.6a) | Data Controller identity, agreement party model (ADR-010, ADR-011) | ◐ | The party model already stores an identity claim set; make the **controller** (not only the station owner) a first-class `assigner` with its own identity and, where the controller is an organisation, a delegation credential for the steward who approves; the owner's station policy is a second, orthogonal assigner | v1 |
| A8 | **Participant status of controllers and of the Individual Gateway.** A data controller in FDT is **an organisation or a natural person** (Luiz, 11 Sep 2026). Rulebook: Participant = "the technical role that represents a legal organisation (not a natural person) and is capable of operating the required software agents"; DCP participant IDs are DIDs of participants; EHDS Art. 73(1)(a),(d) requires "authorised natural persons listed in the data permit" and "individual and unique user identities" *inside* a participant's environment | **Individual Gateway** — the controller-side application through which *one* controller, **whether a company or a person**, exercises control over its data across stations (FDT spec v0.1: "Personal Gateway — application responsible to intermediate the communication between Data Stations and Data Controllers. The Data Controller exercises its/his/her control over the data available in different Data Stations through the Personal Gateway") | ◐ | **Organisation as controller**: no tension — the gateway is that organisation's participant agent (Rulebook: connector/agent "forms the gateway for a participant to a data space"), identified like any participant (A2–A3). **Natural person as controller**: decide between (i) a gateway **operator** (institution, patient organisation, data-altruism organisation) as the participant with the person as *data rights holder / data subject* whose authorisation travels as a credential or DUA (Gaia-X maps GDPR consent to a Data Usage Agreement; DGA data altruism for donation without reward), or (ii) the person running their own agent, which the Rulebook does not foresee and needs a governance exception. Option (i) is alignable today | v1 (decision) |
| A9 | Identity of natural-person controllers behind an Individual Gateway (organisational controllers use the participant identity of A2–A3): eIDAS 2 / EUDI Wallet (Regulation (EU) 2024/1183) is the EU vehicle for person-level VCs; Gaia-X 3.x lists OID4VCI/OID4VP for credential exchange; DCP uses DIDs. *(eIDAS 2 details not verified in this session — check the regulation and the Architecture Reference Framework before relying on them)* | Individual Gateway, Station PEP 1 | ✗ | Design the gateway so that the individual authenticates with a wallet/OIDC identity and the gateway presents *derived* authorisations to stations; keep person identifiers out of agreements except where EHDS requires named persons | v2 |

### C. Policies, negotiation and agreements

| Req. | Requirement | FDT element | Now | Proposal | Horizon |
|---|---|---|---|---|---|
| C1 | "An access policy … always needs to be present, even if it grants access to everyone"; contract policies define attributes needed for an agreement; usage policies "control how the data can be used" (Rulebook §105) | Controller offers (ADR-007) | ◐ | Distinguish the three policy kinds in the FDT ODRL profile; require an access policy on every dataset | v1 |
| C2 | "Before data can be shared, a data contract offer needs to be negotiated to reach a Data Contract Agreement" (Rulebook §110); negotiation may range "from automated negotiation to manual escalation" (§102) | Agreement lifecycle (ADR-008) | ✓ | FDT's matched → pending approval → active is exactly this; keep | v1 |
| C3 | DSP Contract Negotiation state machine REQUESTED → OFFERED → ACCEPTED → AGREED → VERIFIED → FINALIZED, TERMINATED; "Terminal states are final"; each negotiation gets a new IRI; messages Contract Request/Offer/Agreement/Agreement Verification/Event/Termination | Negotiation PDP, Agreement Store (ADR-009) | ◐ | Map FDT states: requested→REQUESTED, matched→AGREED, pending approval = provider-side wait before AGREED, active→FINALIZED, rejected/revoked→TERMINATED; document the mapping; expose DSP messages behind the gateway in v2 | v1 (mapping), v2 (protocol) |
| C4 | DSP ODRL constraints: "All Policy types (Offer, Agreement) MUST contain a unique identifier in the form of a URI"; offers in negotiation "MUST have a `target`" while their rules "MUST not have any `target` attributes"; "An Agreement MUST have a `target` property containing the Dataset identifier", "MUST contain a `timestamp` … XSD DateTime", "MUST contain an `assigner` and `assignee`" | ODRL profile (ADR-007), fdt-commons | ◐ | Encode these as SHACL shapes in `fdt-commons` for FDT offers/requests/agreements now — zero cost, guarantees later DSP compatibility | v1 |
| C5 | Trains as contracted assets: in code-to-data "The consumer participant provides a data asset containing code (source code, compiled library, signed container)" (Rulebook §110); processing services offer "algorithms and code for processing data as a data contract" (§124) | Train, Train Garage, FDT-O | ✗ | Model a Train as an `odrl:Asset` + `dcat:Resource` with its provider's `odrl:Offer` — **not** a `dcat:Dataset` (trains are executables; decision of 11 Sep 2026, ADR-020 as amended) — so a station can negotiate *about the train* as well as about the data; the Garage becomes an FDT catalogue of train offers (`GarageCatalog` via `dcat:resource`). Note the consequence: the DSP Catalog Protocol only carries `dcat:Dataset`, so trains are not DSP catalogue entries; the Rulebook's "data asset containing code" is honoured at the ODRL level (the train is the offer's asset), not by calling it a dataset | v1 (model), v2 (protocol) |
| C6 | Gaia-X data exchange: Data Product Usage Contract must embed Data Usage Agreements from the rights holders; delivery only to consumers that "have formally accepted" the contract and "fulfill the constraints in the Data Usage Agreements" (Compliance D1.1.5–6b) | Agreement model | ◐ | FDT's controller offer ≈ DUA; owner policy ≈ provider terms; document the correspondence; DUA notarisation service optional | later |
| C8 | **A controller's control across stations (organisation or person).** Gaia-X: the DUA "enables Data Rights Holders to control by whom, how and when their data is used (data sovereignty)"; GDPR consent is represented as a DUA; EHDS gives natural persons an **opt-out** from secondary use (Dutch implementation letters) and Art. 61 duties to users; DGA data altruism relies on revocable consent | Individual Gateway, controller offers, Agreement Store | ✗ | Model the controller's conditions as an ODRL offer authored *through* the gateway and attached to their resources on every station that hosts them (the gateway is a multi-station PAP client); make **revocation/opt-out** a first-class event that stations must honour at the next checkpoint (as ADR-013 already foresees for controllers) and that the Handler shows on the itinerary map | v1 (model) |
| C7 | Data Act Art. 36(1) for automated execution of agreements: robustness and access control, "a mechanism … to terminate the continued execution", auditability archive of "transactional data, smart contract logic and code", consistency with the agreement | Orchestrator, PEPs | ◐ | Revocation at next checkpoint + append-only audit already there; add "archive of agreement + policy version + enforcement decision" per job | v1 |

## 4. Impact on the July 2026 architecture decisions

- **ADR-006 (FDP conformance)** — extend: the embedded FDP catalogue should also be a DSP-conformant `dcat:Catalog` (B2, B3). Low cost; FDP and DSP both build on DCAT.
- **ADR-007 (ODRL)** — extend: the FDT ODRL profile adopts the DSP structural rules for offers/agreements (C4) and distinguishes access / contract / usage policies (C1); add "allowed trains / trusted garages", "processing location" and "no re-identification" as profile constraints (D6, F4, F2).
- **ADR-008 (human-in-the-loop)** — confirmed by Rulebook §102 ("manual escalation"); document that the pending-approval state can wrap an external permit decision (EHDS HDAB) (G4).
- **ADR-009 (align with DSP "where cheap")** — widen scope: state-machine mapping for negotiation *and* transfer (C3, D4), plus the well-known endpoint and TCK as the v2 target (B3, H1).
- **ADR-010 (OIDC now, VC-ready)** — specify the VC phase as **DCP** with a chosen profile, and name the governance authority for trusted issuers (A3, A4).
- **ADR-011 (controller ≠ owner)** — maps well onto Gaia-X's rights holder (DUA) vs provider (contract) split (C6); keep, and extend the party model so the controller is a first-class, identified `assigner` (A7). The **Individual Gateway** is the controller-side application for natural persons and small controllers: it needs a decision on participant status (A8) and becomes the home of opt-out and transparency duties (C8, G8).
- **ADR-012 (deployment profiles)** — add an "SPE-conformant" enterprise profile as a design target for 2029 (G1–G3) and an "attested" profile as a later option (D5).
- **ADR-013 (orchestration and choreography)** — Rulebook §110 supports the Handler's monitoring/start/stop role (D3); station-to-station forwarding (P10) needs A5.

Candidate new ADRs (proposed, not decided): **ADR-014** DSP-conformant catalogue and state-machine mapping as the interoperability baseline; **ADR-015** Trains modelled as contracted assets (dataset/offer) with the Garage as their catalogue; **ADR-016** FDT governance function for participation and trusted issuers; **ADR-017** SPE-conformant station profile for EHDS secondary use.

## 5. Questions for Luiz — decisions of 11 September 2026

1. **DSP horizon** — v1: DSP-conformant catalogue, DSP structural rules for offers/agreements as SHACL shapes in `fdt-commons`, documented state-machine mapping; v2: endpoints, `/.well-known/dspace-version`, TCK (ADR-019).
2. **Trains as contracted assets** — yes; the Train Garage becomes a catalogue of train offers (ADR-020). Amended later the same day: a train is an `odrl:Asset`/`dcat:Resource`, never a `dcat:Dataset` ("they are executable things, not datasets"); FDT-O may be edited freely.
3. **FDT governance authority** — per data space / deployment: FDT defines the governance function and interfaces and issues nothing itself; **a station may participate in multiple FDT networks with different governances**, so self-descriptions list memberships and policies are evaluated per network (ADR-017).
4. **May the Handler hold data?** — only non-personal / aggregate data released by a station's result inspection (ADR-015); DGA position still to be checked per deployment (F1).
5. **Gaia-X** — alignable, not compliant (ADR-021).
6. **Individual Gateway** — serves any single controller, company or person; for organisations it is that organisation's participant agent; for natural persons participation is **by deployment profile** — personal profile: person as participant with own gateway; team/enterprise: operator-participant with the person as rights holder (ADR-018).
7. **Data controllers** — a participant class in their own right, organisation or natural person, identified `assigner` of agreements; evidence of authority and steward delegation are v1 onboarding items (A1, A7; ADR-017/018).

## 6. Compute-to-data in the frameworks (for positioning texts)

IDSA Rulebook 2026-2 §110 and §124 are the citable recognition of FDT's model ("code to data"; processing services delivering "code libraries, signed containers, or entire virtual machines"; trustees that "perform the calculations, and then distribute the results"); IDS-RAM 4.2 Data Apps run inside the connector; Gaia-X reaches it through Pontus-X/Ocean Protocol's compute-to-data; the DSSC Blueprint names "data processing services" among participant-agent integrations. No IDSA or Gaia-X text uses the term "data visiting", and no published mapping of the Personal Health Train onto IDSA/Gaia-X was found — a gap FDT could fill with a position paper.

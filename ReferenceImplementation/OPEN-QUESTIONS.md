# Open questions

Questions raised by implementation that the plan does not settle. Each carries the
conservative default that is in force until it is answered, so work continues; code that
depends on one is marked with its id.

Decisions **D1–D5** belong to Luiz Olavo Bonino da Silva Santos (plan §7). D1, D2 and D3
were taken on 12 September 2026 and are recorded here with what was decided.

---

## Answered

### D1 — Handler and Gateway implementation language
**Answered 12 Sep 2026: Python 3.12, alongside the station.** The Java 17 / Spring Boot
prototypes (`TrainHandler`, `TrainHandler-server`, `TrainHandler-client`, `TrainOrchestrator`)
stay where they are as the prototype lineage; they are not evolved. One stack, one set of
generated models, one test harness.

### D2 — Location of the FDT-O ontology file
**Answered 12 Sep 2026: `FAIRDataTeam/FDT-O` is canonical.** The v2 merge is
[PR #1](https://github.com/FAIRDataTeam/FDT-O/pull/1) on branch `fdt-o-v2`, which the
metaproject pins until it lands. See Q1 and Q5.

### D3 — Console technology
**Answered 12 Sep 2026: React 18 + TypeScript + Vite**, one codebase with three role-based
apps (`FDTConsole`). The design system comes from `mockups/gen/base.py`; contract types are
generated by `openapi-typescript` from `fdt-commons/protocol/openapi/`.

## Open

### Q1 — Publishing the contracts at their `w3id.org` IRIs
**Blocks:** the second clause of WP-0.2's acceptance ("`fdt-commons` profile `owl:imports`
resolves"), and any third-party consumer (WP-4.4).

Three IRIs are referenced but resolve to nothing:

| IRI | Referenced by | Served from |
|---|---|---|
| `https://w3id.org/fdt#` | every shape, every example, the ontology | `FDT-O/ontology/fdt-o.ttl` |
| `https://w3id.org/fdt/run/context.jsonld` | `examples/plan-time-to-groin.jsonld` | `fdt-commons/contexts/fdt-run.context.jsonld` |
| `https://w3id.org/fdt/v2-delta` | `vocab/fdt-profile.ttl` `owl:imports` | `FDT-O/ontology/fdt-o-v2-delta.ttl` |

`FAIRDataTeam/w3id.org` exists, so this is redirect configuration rather than new
infrastructure. **Default in force:** validators resolve all three locally and never touch
the network, so CI is offline and deterministic (`fdt-commons` FINDINGS.md finding 13). This
is correct for CI and wrong for anyone outside the project.

### Q2 — The `dspace:` namespace IRI for DSP 2025-1
**Blocks:** nothing in v1; blocks the v2 DSP binding (ADR-019).

`fdt-commons` assumes `https://w3id.org/dspace/2025/1/` and that `timestamp` is the
property's local name in the published JSON-LD context. Neither was verified against the
published context (`FINDINGS.md` finding 11). **Default:** keep the assumption, and keep the
DSP mapping as documentation only (`mapping/state-machines.md`). Do not let a v2 binding
reach the protocol server — the visit protocol is FDT's own until ADR-019's v2 step.

### Q3 — D4: first target networks and identity providers for the compose demo
**Blocks:** WP-1.2 trusted-issuer configuration.

**Default (from the plan):** a fixture OIDC provider in compose, with the fictional networks
of `examples/network-and-stations.ttl`. Nothing depends on a real IdP until someone asks for
a deployment against one.

### Q4 — D5: vendoring the JMESPath library
**Blocks:** nothing any more. **The premise has expired.**

D5 exists because no package registry was reachable during the design sessions. PyPI is
reachable from the implementation environment — `pyshacl`, `rdflib` and `jsonschema` were
installed from it to produce the M0 results. **Default:** depend on the published
`jmespath` (declared in `FAIRDataTrainHandler/pyproject.toml`) and do not vendor. WP-2.1
must still run `tests/conditions.cases.json` against it, because the compliance question —
does this implementation agree with the spec? — was never the same question as the
availability one.

### Q5 — FDT-O: retiring the `https://w3id.org/fdt/fdt-o#` namespace
**Blocks:** the `FDT-O` submodule moving from `fdt-o-v2` to `master`.

[PR #1](https://github.com/FAIRDataTeam/FDT-O/pull/1) unifies the term namespace on
`https://w3id.org/fdt#` and keeps the prototype IRIs as deprecated `owl:equivalentClass` /
`owl:equivalentProperty` bridges. It is a PR and not a push because retiring a published
namespace is Luiz's call. **Default:** the metaproject pins the branch, so `make check` is
green either way.

### Q6 — Repository visibility
The seven repositories created on 12 Sep 2026 (`fdt-commons`, `FAIRDataStation-py`,
`FAIRDataTrainHandler`, `IndividualGateway`, `StationDirectory`, `TrainGarage`,
`FDTConsole`) are **private**, by decision, until M1 runs. `FDT-O`, `FAIRDataTrain`,
`FAIRDataStation` (Java) and the `TrainHandler-*` repositories are public and unchanged.
**Default:** flip to public when the M1 scenario passes. Note that WP-4.4 — "a station
implemented only from `fdt-commons` plus the conformance material passes the suite" —
cannot be demonstrated by a third party while `fdt-commons` is private.

### Q7 — What becomes of the Java prototypes
`FAIRDataTeam/FAIRDataStation` (Java/Maven, active to May 2025) keeps its name; the ADR-001
station is `FAIRDataStation-py`. Similarly `TrainHandler-server` / `-client` and
`TrainOrchestrator` are untouched. A newcomer searching the organisation will find two
things called a data station and four called a train handler, and no marker saying which is
current. **Default:** leave them alone; say in each new README what supersedes what. A note
at the top of each prototype's README, or archiving them, would be clearer — but it changes
public repositories, so it waits for a decision.

### Q8 — The GitHub token in `FDT-O`'s history
`example-instances/sparql-train-payload.ttl` carried a GitHub access token in a payload
download URL, in a public repository. PR #1 removes it from the file; it remains in the
history. It is a `GHSAT0` GitHub App token, which expires within 24 hours of issue and was
committed in 2022, so **the exposure is long over**. **Default:** leave the history alone —
rewriting it breaks every existing clone and fork for a credential that cannot be used.
Revisit only if a scan flags it.

### Q9 — WP-1.3's acceptance criterion names a fixture that does not exist
**Blocks:** WP-1.3's acceptance as written.

The criterion reads: "the fixture offer `evt-registry-research` and request `ttg-2026q3`
produce an agreement equal in structure to `agr-9a01`; **the HealthAI commercial request is
Refused with the prohibition named**." The first half is runnable — all three IRIs are in
`fdt-commons/examples/policies.ttl`. The second is not: **there is no HealthAI request
fixture**, and `policies.ttl` declares exactly one `odrl:Request` (`ttg-2026q3`). HealthAI
B.V. appears only in the mock-ups' sample data; the vocabulary it would need
(`fdt-p:consumerType`, `fdt-p:Commercial`) exists in `vocab/fdt-profile.ttl`, but no
instance uses it.

Refusal on a commercial purpose is the one path that exercises an ODRL **prohibition** end
to end, and it is the S3/G4 denial the consoles are designed around — so this is a missing
fixture, not a criterion to drop.

**Two further defects in the same criterion** (FINDINGS 19, 20), found while building the
evaluator against it:

- **`agr-9a01` is not derivable from the offer and request it names.** Both carry
  `fdt-p:legalBasis`; the agreement drops it while keeping `onwardStateClass` and
  `carryOnward`. No ODRL rule keeps one constraint and discards another, so "produce an
  agreement equal in structure to `agr-9a01`" asks an implementation to reproduce an
  inconsistency. The fixture and the derivation rule must be settled together.
- **The work package is the auto-approval path, and the named offer requires manual
  approval.** `evt-registry-research` carries `fdt-p:requiresManualApproval true`, and the
  protocol event fixture confirms `matched → pending-approval → active`. No offer in the
  fixture set reaches `active` without a person, so the path M1 depends on has no fixture.

**Default:** add `ex:request\/healthai-2026q3` (assignee HealthAI B.V., `fdt-p:consumerType
fdt-p:Commercial`) and the matching prohibition on the `evt-registry-research` offer to
`fdt-commons/examples/policies.ttl`, under the change protocol — fixture first, version
bump, `FINDINGS.md` line — before WP-1.3 writes any evaluator code against it. Until then,
WP-1.3 can only demonstrate its first half.

### Q10 — Are the other work packages' acceptance criteria runnable?
**Blocks:** nothing yet; it decides whether each work package starts on solid ground.

WP-1.3's criterion contains **three** independent defects — a fixture that does not exist
(Q9), a target agreement that is not derivable (finding 19), and a named path that the named
fixture cannot reach (finding 20). That is not bad luck. The criteria were written against
fixtures nobody had executed, in design sessions where no validator could run — the same
condition that produced findings 12–14.

**Default:** before a work package starts, check its acceptance criterion for runnability —
do the fixtures it names exist, are they internally consistent, and do they exercise the path
the criterion claims? Record what is missing and fix the fixtures under the change protocol
*first*. Doing this at the point where the tests fail instead means the pressure is on to
bend the code to a broken fixture.
